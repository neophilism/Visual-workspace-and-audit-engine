# Private processing reconciliation controls

The opt-in `./reconciliation-client` and `./reconciliation-controls` subpaths use Processing PR17, pinned at `44d76aefb8701852398182a158248c1b6b7a8fda`. They require an authenticated private HTTPS host, an explicitly supplied transport and expected tenant/project. Mounting requires the document's exact origin. This is a library component, not a listening server, session issuer or deployment.

`new ReconciliationClient(origin, scope, transport, timeoutMs?)` uses only GET `/processing/session` and POST `/processing/reconcile`. Each explicit reconciliation first obtains fresh session CSRF. The POST contains exactly the reviewed job ID, original consumed revision and one explicitly selected action: recover committed output (`recover-stored`) or finalize existing encrypted private bytes (`finalize-existing`). Backend current authentication, manager lists, policy/content checks, ledger bindings and encrypted objects remain authoritative. There is no execution, consume, retry, no-output settlement, cleanup, source download, grant, sending or publication control.

`mountReconciliationControls(root, client)` provides labelled fields and an explicit action selector with no action selected initially. The operator must review the consumed execution from a separately authorized task view. Successful completion returns only exact private references and the acknowledged job revision. It is historical acknowledgement, not a current task subscription, receipt re-attestation or action permit. Refresh the current authorized task view separately. The component never changes the offline export or its network policy.

The client captures input before awaiting session/transport work. Before a POST can be observed it retains the exact immutable request in memory. Network errors, invalid responses, timeouts, server diagnostic phases and even definitive HTTP rejection keep that request locked conservatively. No other execution/action can be submitted on that client. Resolve exact pending request is an explicit replay of the same envelope after fresh session CSRF; it never switches recovery mode. It may finish the requested recovery if the original POST never arrived. There is no automatic retry, polling, fall-through from recovery to finalization, rollback assertion or absent/stopped-output inference. A diagnostic phase is only a diagnostic phase.

Responses require strict UTF8 JSON, no-store, no redirect and fixed paths, bounded to 256KiB/4096 chunks. The default 15-second deadline applies separately to each HTTP exchange and covers transport and response body with monotonic gates. Timeouts are configurable from 10 to 30000ms. Owned signals close on every exit; a host transport can ignore cancellation or complete a server operation after timeout, so unknown outcomes remain pending. Begun backend SQL/filesystem work is not rolled back by a client timeout. Completed results require the exact job/revision and exact private artifact/receipt reference schemas, matching scope and edition. These metadata checks do not independently decrypt bytes or replace backend verification.

CSRF exists only in the current request's memory, never DOM or browser storage. Scope is captured at construction. Once a session actor is observed, a changed actor permanently closes the client before another POST. The host MUST dispose/recreate clients on logout, identity or policy-context changes; actor IDs alone cannot detect replacement sessions for the same actor. The backend session route does not return purpose, so purpose binding is configured and enforced by the host/backend, not inferred here. The host must configure secure cookies, TLS/proxy, CSP restricting connect-src, private authorization for task views, sensitive-log redaction and rate/concurrency limits. Client checks do not authenticate users.

Disposal aborts outstanding requests and prevents late updates even to detached UI. It retains any immutable pending request for explicit host review through the getter; it does not certify cancellation or server rollback. Pending input/results are memory-only. Closing/reloading the page or disposing/replacing the component needs separately designed private recovery UX/storage; crash/reload recovery is not implemented. A closed client cannot issue a replay. Recreate only after host review of exact execution and current server state; never bypass uncertainty by creating replacement job IDs.

Tests execute the pinned installed Processing handler, coordinator, actual canonical SQL migration under restricted authenticated PGlite, ledger and temporary AES-GCM output store. A forced transaction rollback leaves actual pending encrypted bytes; finalization/completion and explicit replay use those existing bytes with object writes disabled. Other tests use synthetic Response/ReadableStream adversaries and JSDOM. These do not establish independent TCP-session contention, real browser/assistive-technology acceptance, listening HTTP/TLS/session deployment, production identity/source/liveness or crash/power-loss qualification. Source callbacks and policy are controlled neutral test fixtures. No real input, provider, paid infrastructure, sending or public publication is used.

Remaining work includes authenticated host/current Identity wiring, integrated task navigation, private crash/reload recovery, browser/accessibility acceptance and qualified production proof/liveness services. The suite remains incomplete and PAM stays last.
